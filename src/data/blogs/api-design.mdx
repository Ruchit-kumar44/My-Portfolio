# API Design Fundamentals I Wish I Knew Earlier

Building the `/api/contact` route for this portfolio pushed me to actually think about API design instead of just making something that technically works. A few things that made the biggest difference.

## Use the right status code, not just 200 or 500

- `200` — success
- `400` — the client sent bad data (missing fields, invalid format)
- `404` — the thing being asked for doesn't exist
- `429` — the client is sending too many requests
- `500` — something broke on the server, not the client's fault

Returning `200` for everything, with an `{ error: "..." }` body for failures, forces every caller to parse the body just to know if something went wrong. A correct status code lets simple checks like `if (!res.ok)` work without reading anything else.

## Validate on the server, always

Client-side validation is for user experience — instant feedback without a round trip. It is not security, and it is not a substitute for server-side validation, because anyone can send a request directly to your endpoint, bypassing your form entirely.

```ts
if (!name || !email || !message) {
  return NextResponse.json({ error: "All fields are required." }, { status: 400 })
}
```

A library like Zod makes this easier to get right, since the validation rules live in one schema instead of a chain of manual `if` checks.

## Keep resource names as nouns, not verbs

A decent convention:

- `GET /api/projects` — list projects
- `GET /api/projects/:id` — get one project
- `POST /api/projects` — create a project
- `DELETE /api/projects/:id` — delete a project

The HTTP method already describes the action. `/api/getProjects` or `/api/deleteProject` duplicates that in the URL itself, which usually means the API grew without a consistent naming rule from the start.

## Rate limit anything public

Any endpoint reachable without authentication — a contact form, a public search — can be hit repeatedly by a script, not just a human using the page. A simple per-IP request counter with a time window stops the easy cases without needing a paid service.

## Takeaway

None of this is advanced. It's mostly about treating an API's shape as something worth deciding on purpose, rather than whatever came out while making the first request work.
